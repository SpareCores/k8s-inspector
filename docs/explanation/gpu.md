# GPU nodes

GPU benchmarks (nvidia_smi, nvbandwidth, llm, vllm, ffmpeg on GPU types) are a later phase. The first vendor (OCI) has
no GPU types in scope, so the GPU phase starts with AWS ([roadmap](../roadmap.md)). The node side is a **planned
SCarpenter feature**: the NVIDIA driver sysext and the NVIDIA container runtime, selected per NodeClaim from the
accelerator labels. k8s-inspector only selects the runtime class and makes the adaptive decisions. The section below
summarises what k8s-inspector expects from that feature.

## Node side (planned SCarpenter feature)

| Piece | How |
|---|---|
| Kernel driver | Flatcar's **prebuilt NVIDIA driver system extension**, built with every Flatcar release and matched to its kernel. Enabled by listing it in `/etc/flatcar/enabled-sysext.conf` (Butane `storage.files`), for example `nvidia-drivers-570-open`. No compilation on the node (the fallback `nvidia.service` compile takes 5-10 minutes). |
| Driver branch | Chosen per NodeClaim from the catalog's accelerator model (the node already carries `accelerator-manufacturer` and `accelerator-model` labels): Turing and newer → open modules; pre-Turing (Volta, Pascal, Maxwell) → proprietary modules of branch ≤ 580 (580 is the last branch that supports them). A small mapping table with a per-NodeClass override. SCarpenter renders the choice into the node's Ignition. |
| Container runtime | The `nvidia-runtime` sysext (container toolkit) and a containerd runtime handler `nvidia`, or CDI specs generated by `nvidia-ctk cdi generate`; a `RuntimeClass nvidia`. |
| Host settings carried over from sc-inspector | `nvidia_drm modeset=0`, no runtime PM, no DRM autoload (headless GPUs otherwise loop in udev), `NVreg_PreserveVideoMemoryAllocations=1`, persistence mode (`nvidia-smi -pm 1`). |
| Device plugin (GPU nodes only) | Karpenter marks a NodeClaim initialized only after every extended resource of its instance type, including `nvidia.com/gpu`, is registered on the Node, so SCarpenter runs the NVIDIA device plugin as a lean DaemonSet on GPU nodes. The node still belongs to one run: inspector Pods request all of the node's `nvidia.com/gpu` and set `runtimeClassName: nvidia`. |
| No GPU Operator | Its driver containers do not fit Flatcar's read-only `/usr`; with host driver and toolkit it would only add monitoring on top of the device plugin. |

### Branch availability (Flatcar release servers, at the time of writing)

| Channel | Prebuilt branches |
|---|---|
| stable, beta | 535, 550, 570 (open and proprietary) |
| alpha | additionally 580 (open and proprietary) |

No 590 yet. Pre-Turing GPUs therefore need 580 proprietary from alpha, or 570/535 if the specific GPU is still
supported there. The sysext is tied to the Flatcar version: GPU NodeClasses pin the same Flatcar version as the
driver file.

### Speed

The driver file is 430-570 MB. SCarpenter mirrors the pinned `.raw` files (with their sha256 from `.DIGESTS`) into
object storage in each vendor's region and points Ignition there, which avoids the Flatcar CDN hop and helps regions
with poor routing. A pre-baked GPU image per vendor would remove the download entirely, at the cost of one image per
vendor, region, Flatcar version and branch; it is not planned.

### Known pain points

- GRID/vGPU and fractional GPUs (AWS GRID types, Alibaba `vws`) need vendor drivers that the Flatcar sysext does not
  ship; they stay unsupported (decision K15).
- AMD GPUs: no sysext; unsupported.
- arm64 GPU sysexts are not documented by Flatcar; amd64 only until verified.
- Large images (vLLM GPU) and model downloads dominate run time; GPU runs get a 256 GiB root disk, a 6 h
  pre-launch budget (GPU capacity is scarce) and a 45 min `readyMinutesGpu` deadline from registration to the
  NodeClaim's `Initialized` condition (driver install, device plugin). The node registers with the
  `scarpenter.sparecores.com/gpu-pending` taint until the NVIDIA check passes; the anchor does not tolerate it. A node
  whose driver check fails stays tainted and the run ends `BOOT_FAILURE` at the deadline.

## k8s-inspector side

- **GPU first, then CPU.** On GPU types every step uses `runtimeClassName: nvidia`. If a container never ran its task
  (a container start error, `sc-run` failing itself with exit `256`, or an image pull timeout), only the
  containers that did not start are recreated once without the runtime class, except when a failed container's task needs the GPU or is the vLLM GPU
  image (the ladder moves on to the CPU images). A non-zero exit of a task that ran is final, as today.
- **GPU facts.** A `gpu_facts` container in the probe step reports VRAM and compute capability; they drive the vLLM
  image ladder (skip the GPU image below compute capability 8.0) and the nvbandwidth buffer size (512 MiB, 256 MiB
  up to 2 GiB of VRAM or when the VRAM is unknown).
- **Precheck.** A GPU task planned on a node without an NVIDIA accelerator label or lshw entry ends as `-3`.
- vLLM gets `/dev/shm` of 4 GiB; llm and vllm share a per-node model cache (hostPath).

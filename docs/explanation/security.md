# Security

Benchmark containers are privileged by necessity (raw disks, DMI, `/dev/kvm`, `nice -20`, rlimits). A privileged
container can read the whole node. The design therefore keeps **nothing valuable on benchmark nodes** and keeps
benchmark nodes away from everything else ([separation](separation.md)).

## Credentials

| Credential | Where it lives | Who can use it |
|---|---|---|
| Object storage (write and read the output prefix) | none stored: the controller's ServiceAccount token is exchanged for a cloud IAM role session through the cluster's OIDC issuer; the role needs `s3:GetObject`, `PutObject`, `DeleteObject` (stale task files before a launch), `ListBucket` and the multipart actions under the run prefix | the controller only |
| Output upload URLs | the run's Secret, mounted into step Pods | anyone holding the URL, for that one key and method, until it expires (≤ 12 h) |
| Git deploy key (write to sc-inspector-data) | Secret mounted only into the controller | the controller only |
| Keeper API key (if required) | controller Secret | the controller only |
| Benchmark secrets: Sentinel token, geekbench licence passphrase, Hugging Face token | `inspector-secrets`, injected only into the tasks that need them (HF token: llm and vllm only) | those step containers |
| DBaaS vendor credentials | Secret `k8s-inspector-dbaas-<vendor>` as environment of the `dbaas-*` Jobs only, or workload identity of their ServiceAccount | provisioner Jobs only |
| Pulumi state bucket access (`dbaas-state/`) | the role `K8SI_DBAAS_ROLE_ARN`, a web identity token projected into the `dbaas-up` and `dbaas-down` Jobs and named in an AWS profile (no `AWS_*` variable, so the vendor's providers never get it); limited to `dbaas-state/`, not the controller's role | those Jobs |
| Pulumi state passphrase | Secret `k8s-inspector-dbaas-state` as environment of the `dbaas-*` Jobs | provisioner Jobs only |
| Database password | generated by the controller per run, Secret `<run>-db` owned by the run (also encrypted in the Pulumi state) | the pgbench step, the bootstrap Pod and the provisioner Job |

`inspector-secrets` has one key per secret, and the key name is the one used in the catalogue's `secrets` list:

| Key | Environment variable of the container | Tasks |
|---|---|---|
| `sentinel` | `SENTINEL_API_TOKEN` | every benchmark task |
| `geekbench` | `BENCHMARK_SECRETS_PASSPHRASE` | geekbench |
| `huggingface` | `HF_TOKEN` | llm, vllm |

Secrets come from the cluster's secret store through External Secrets; none are in this repository. Benchmark Pods run
with `automountServiceAccountToken: false` and have no RBAC. So do the DBaaS Jobs: they report through their
termination message and have no Kubernetes API access (their ServiceAccount has no Role), so a compromised provider package
cannot read other Secrets.

## Instance metadata (IMDS)

The vendors' metadata services serve each node's user-data, which holds the node's bootstrap material. By default
SCarpenter lets only an allowlist of its own host units reach the metadata service; other host processes, Pods and
hostNetwork Pods get nothing. `spec.instanceMetadata.access: Open` on an SCNodeClass lifts the restriction.

On the bench NodeClass the setting is `Open` (decision K17): the resource tracker inside every benchmark image detects
the cloud through the metadata service, and a privileged container could read the node's disk anyway, so a restriction
would protect nothing there. All other NodeClasses keep the default.

On AWS the bench NodeClass also sets the IMDS hop limit to 2 (`httpTokens` stays `required`, IMDSv2 only). SCarpenter's
default hop limit is 1, which drops the token reply at the veth hop of a Pod with its own network namespace, so the
tasks with `host_network: false` ([loopback tasks](node-profile.md#loopback-tasks)) could not detect the cloud. A node
started before the setting keeps hop limit 1 (the bench pool does not replace drifted nodes). Later the controller can pass the cloud facts to
the tracker as environment variables, and bench nodes can return to the default.

The node's tailnet credential is the remaining sensitive item on a bench node. Mitigations: a tailnet ACL tag that
lets bench nodes reach only what they need, and per-node tailnet keys in SCarpenter before vendors beyond the pilot
are switched over ([roadmap](../roadmap.md)).

## Admission and RBAC

- A `ValidatingAdmissionPolicy` (cluster platform) denies the bench taint toleration, `privileged`, `hostPID` and
  hostPath outside the `inspector` and `kube-system` namespaces, and inside `inspector` allows Pod creation only by the
  controller's ServiceAccount.
- The controller's RBAC is exactly what the code calls (`deploy/controller/rbac.yaml`; a test pins the sensitive
  rules). In `inspector`: Pods (create, list, watch, delete), `pods/exec` (get, create; the heartbeat `exec` between
  steps is a websocket upgrade), Secrets (create, get, update, delete; no list or watch, so it cannot enumerate
  `inspector-secrets` or the platform Secrets), ConfigMaps (get, create, patch; `k8s-inspector-spot` and `k8s-inspector-launch-<vendor>` are created on first
  use), `benchmarkruns` (create, get, list, watch, patch, delete) and `benchmarkruns/status` (patch). Cluster-wide:
  get Nodes; list Pods (the CPU requests of the Pods on the benchmark node, see [CPU weight](node-profile.md#cpu-weight)); get, list and delete NodeClaims (the stale node of an attempt). Nothing else.
  The cluster-wide `pods list` lets the controller read every Pod spec in the cluster, including inline `env`
  values. This is accepted: the field-selected list per node is needed to see the kube-system, flannel and debug
  Pods, and RBAC cannot restrict a list by field (only by namespace or name).
